Authors: https://github.com/Tranway1/buff

Section 3.3 describes majority-byte / sparse outlier coding. Section 4.4.1
explicitly attributes GPS/Stock size improvements to it. The paper's BUFF
results therefore include this optimization; the text does not justify treating
our scalar plain encoder as equivalent to every published BUFF result.
Section 4.4.2's Fast-BUFF is a separate optimization: user-provided range
statistics avoid a range scan. We do not supply oracle range statistics.
Repository script float_compress_simd.sh evaluates buff, buff-simd and buff-major
separately. Its log parser reports compression/decompression and analytical
queries, not isolated random-point latency. Do not infer point-access speed
from those query figures.

The original buff_major_decode_condition looks like a selective decoder, but
its outlier_cols > 0 branch only logs:
  conditional mat for buff major is not implemented yet!
Thus the original majority implementation cannot supply the same native point
access API as the plain implementation when sparse columns actually occur.
Full decoding works. A bitmap/rank point decoder would require new code; we have
not invented one or applied arbitrary 1k blocking to label it native access.

Original majority routines were extracted for an isolated audit, not substituted
in the production BUFF adapter. 32 head/tail samples, 16 datasets, at most 205825
values per sample; BP/BM/BT/BW fit fully, so their head/tail samples duplicate.
CPU 18 on the benchmark server; five medians after one warm-up; alternate encoder
order; both routines compute their own ranges; no byte-buffer clone timed for
plain decode, majority's original decoder consumes the encoded vector.
Sources and measurements: benchmark_results/20261105-competitor-audit/buff-majority.
All 32 majority decodes equal plain's bounded-precision outputs bit for bit.
This does NOT make BUFF bitwise lossless against input binary64.
Seven samples save space, 4.39--44.96%; the rest cost one additional format byte.
Median majority/plain compression throughput ratio across samples: 0.943.
Selected size reductions and MiB/s (plain -> majority):
  BW head: 19.38%; encode 566.7 -> 494.3; decode 620.7 -> 586.8
  DU tail: 44.96%; encode 1258.8 -> 1110.1; decode 2241.4 -> 1982.9
  LAT head: 7.87%; encode 550.0 -> 466.5; decode 726.7 -> 589.1
  LON head: 4.39%; encode 635.0 -> 512.3; decode 792.7 -> 607.2
These are sample diagnostics, not full-dataset publication measurements.
The repository compares a Boyer-Moore residual vote counter against
SAMPLE * MAJOR_R, with MAJOR_R=.6; this is not a literal 60% frequency test.
Paper section 3.3 describes a greater-than-90% frequency test.
Do not present the extracted repository variant as an exact reproduction of
all paper parameter choices.

Gorilla
Now uses Facebook Beringei value-codec and bit-I/O method bodies, extracted from
commit 75c3002b179d99c8709323d605e7d4b53484035c. Full source, license, patent grant,
method hashes and reproducible extractor are retained in lib/beringei-value and
tools/import_beringei_value.py. Adaptations: standard string/string_view replace
Folly containers, bit_cast replaces aliasing pointer casts, inline linkage.
Original initial state, cost-aware XOR-window choice and 6-bit (width-1)
encoding are preserved. No timestamps are fed to this value-only benchmark.
Counts actual byte-rounded payload, without our old extra 64-bit padding.
The old port destroyed an XOR bit and omitted the cost-based window choice.
32 real samples / 5507968 values now round-trip bitwise. Sanitizer regression
covers arbitrary IEEE patterns, signed zero, infinities, NaN payloads, 64-bit XORs
and independent blocks/tails. Main benchmark now checks exact bits.

Camel
Recovered authors' repository as lib/camel-upstream, commit
c4b55c2226163b0bfb6c330aa78b7c0a97d872b3.
The production benchmark now executes the authors' Java codec, not the former
extended C++ port. Run tools/build_camel_java.py (Python 3.8+, Java 8 JDK and Maven) first.
It builds into build/camel-java; alternative build path supports --build-dir.
The C++ bridge reads that build's classpath or GEF_CAMEL_CLASSPATH.
Codec source configurations explicitly documented by the authors' README:
DECIMAL_MAX_COUNT=3 -> 4; integer-difference width remains 16 except LAT,
where it is 19 (maximum within-block difference is 360000). Encoder, decoder
and the legacy size counter are configured consistently. Build this second
configuration with --build-dir build/camel-java-int19 --integer-bits 19 and
select its classpath through GEF_CAMEL_CLASSPATH. No algorithm changes. The two-bit decimal-count field supports 1--4;
we do not add an 18-decimal extension, a raw fallback, or a brute-force decoder.
The legacy C++ headers are retained only for historical diagnostic reproduction.
Original Camel (pure compression, not CamelTree) uses 1000-value blocks. Keep
partial tails; don't follow the authors' benchmark's practice of dropping them.
Warm-up, JVM startup, input transport and validation are outside codec timers.
Record actual query counts. Full, point and cross-block range decode use the
original decoder. The original API has no direct point decoder for this format.
Original getSize() omits the integer sign bit; count the actual OutputBitStream
writtenBits() after close, including byte rounding. A 100000-byte allocation is
capacity, not compressed size. Trim and decode exactly the measured bytes.

Original Java audit: default3 fails 12/32 samples (1308141 changed values);
configured4 fails 8/32 (902348 changed values), namely AP/BM/BT/BW head and tail.
24/32 configured4 samples pass. This is upstream precision/range behavior;
fixing the adapter does not turn unsupported data into lossless Camel data.
The adapter emits measurements and a warning for changed values and marks the
row bitwise_failed, rather than aborting the entire benchmark. JVM/setup errors
emit validation_status=error and NaN ratio. Such rows are not lossless candidates.
Source audit, untouched-Java comparison and adapter checks are under
benchmark_results/20261105-competitor-audit/camel-original.

Competitor fidelity audit, 2026-11-05

Scope and method
32 head/tail samples from 16 real datasets, up to 205,825 values per sample.
Total 5,507,968 value observations. BP/BM/BT/BW each fit within the limit and
are tested in full twice; other samples can overlap. Samples are not a substitute
for full-dataset acceptance. Precompute binary64 inputs with strict division;
feed identical bits to GCC 13.4 -O3 -march=native builds with strict FP flags
versus -ffast-math. Sequential CPU 18 tests, separate from CPU 8 ALP timing.
Original per-codec APIs and 1,000-value external blocks match the suite for the
stream codecs; DAC and BUFF receive the full sample in their native layouts.
All test code/evidence is in this directory. No affected production codec other
than ALP was silently rewritten or replaced.

Priority findings

DAC: no observed inflation bug. All 32 sample sizes are identical between
strict and fast builds. Every integer decodes exactly, the serialized byte
stream matches sdsl::size_in_bytes, and reopening reproduces all values.
This is the original vendored sdsl::dac_vector_dp, default 64-level limit,
whole-column storage, no forced 1k wrapper. Its DP cost model does use floating
arithmetic but did not choose differently in this test. The suite shifts
negative columns to nonnegative values; positive columns retain their absolute
magnitude plus one. DAC encodes those magnitudes with levels/continuation bits
and rank support; it does not use GEF's temporal gaps or local partition models.
Its higher size alone is not evidence of unfair accounting. Original scale/
shift restoration metadata are not counted by this legacy wrapper, which would
slightly UNDERstate complete framing, not inflate it. Each sample uses its own
minimum; exact full-dataset ratios still come from the original full run.

BUFF: no C++ fast-math inflation. Actual encoded bytes (not merely lengths)
match in every strict/fast comparison because the encoding executes in Rust.
All sample outputs meet the declared precision bound. Counted size is the exact
returned vector including 16-byte FFI header. The native fixed-width format's
per-value width is set by the global range and configured decimal precision;
this can be large even for smooth, locally compressible values.

Important variant gap: the current entry calls byte_fixed_encode, exactly the
authors' plain scalar 'buff' profiler route. The paper also describes outlier
handling (section 3.3). The authors provide a SEPARATE 'buff-major' route using
buff_encode_majority. An isolated extraction of their original majority encode
AND decode bodies, original bit-vector library, original Snappy bitmap helper,
and original SAMPLE=2000 / MAJOR_R=0.6 constants shows smaller output on 7/32
samples. All decoded outputs match the plain variant bitwise. Reductions:
BW full dataset 19.38%; DU head 37.52%, tail 44.96%; LAT head 7.87%;
LON head 4.39%, tail 18.40%. The other 25 samples add just one format byte.
These comparisons are native payloads with the same original precision.
This is a material missing optimization/variant, not fabricated plain-codec
sizes. The plot now names BUFF (plain). Majority should be evaluated next, but
its different format cannot be fed to the current plain selective decoder;
size and native-access behavior must be integrated and validated together.
No majority performance results are claimed here.

Gorilla: LOSSLESSNESS FAILURE in both strict/fast builds.
280,216 differing values on 11/32 samples. The compressor mutates the XOR
when leadingZeros==trailingZeros, clearing its last bit. For leading/trailing
counts both zero this destroys information. It also avoids correctly encoding
a 64-bit significant width as six-bit zero. An isolated diagnostic removes the
mutation and masks the width to six bits; all 32 sample round trips then pass.
This diagnostic is NOT deployed to the production adapter or chart values.
Maximum observed absolute error is 1.81899e-12, below the existing 1e-9 check.
Even small changes violate binary64 losslessness. The large reported ratio
cannot be treated as a valid result for a correct Gorilla implementation.

Camel: LOSSLESSNESS FAILURE in both strict/fast builds.
39,275 differing values on 19/32 samples. The current decimal port reconstructs
integer and fractional parts with floating arithmetic and uses epsilon-based
precision decisions. Maximum observed error is 1.42109e-14; all differences
are below 1e-9. The current tolerance validation masks the issue. This requires
comparison with the original implementation/decimal reconstruction, not merely
changing compiler flags. Sample compression sizes are unchanged by fast-math.

Falcon: COMPILER-DEPENDENT LOSSLESSNESS FAILURE.
Strict build: every sample value is bitwise correct. Fast build: 5,498,049
mismatches on all 32 samples (max error 4.36557e-11; all below 1e-9).
Its reconstruction uses pow(10, decimal_places) and floating division, which
are unsafe to optimize algebraically for a bitwise-lossless contract. Payload
size is unchanged in the size audit, so a ratio-only check would miss this.
It needs strict FP compilation of the codec and bitwise validation, followed
by fresh timings. The current suite compiles it in the fast-math main TU.

Chimp, Chimp128, TSXor, Elf: no changed sample sizes and zero bitwise mismatches
under either set of compiler flags. Most of their higher sizes are consistent
with their representation/bit-pattern compression and external stream blocks.
The common legacy wrappers omit a persistent block directory and some padding
from size accounting; this tends to UNDERstate sizes, not explain high sizes.
This test is not a proof for arbitrary inputs or every full dataset.

Other entries: source/build review
DeXOR, Elf*, SElf*, FLEA already use strict FP translation units. Pcodec and
Fauna/Macaque core implementations are Rust. Fauna/Macaque float32 conversion
is a separate declared change of representation, not lossless binary64.
The integer lossless general-purpose codecs do not receive float conversion.
No additional empirical certification is implied for these entries by this
audit. Pcodec/Fauna access qualifications remain as previously documented.

Plot handling
All 16 corrected ALP full cases passed. The requested prepool plot retains its
original 14 common datasets and replaces every ALP metric from the fresh run.
ALP's arithmetic mean compressed/original percentage changes 32.344541 ->
26.979270. Gorilla/Camel/Falcon remain visible but hollow and excluded from the
lossless frontier. BUFF is explicitly plain and precision-bounded. Original

promoted to successful lossless measurements.
